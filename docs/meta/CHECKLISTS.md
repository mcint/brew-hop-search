  What definitely changes, and what to check, at each of the three grains.

  under the next version's heading. Per PR: CI on every matrix entry,
  changelog merges under one heading, docs paths, beads. Per release: the
  owner's sequence plus the things outside this repo that name the version
  (the tap formula, its resources and -V test string, the GitHub release,
  PyPI). "Definitely" means a release is wrong without it; "check" means
  look, it may be a no-op.

# Checklists

## Per commit

Definitely:
- A new feature or fix ships with its test in the same commit (red first;
  a snapshot's first run is the red).
- A user-visible change updates its spec in the same commit
  (`docs/specs/features/*` or a draft), never commit-after.
- A user-visible change adds a bullet to `CHANGELOG.md` under the next
  version's heading (`## [0.3.8]` while `VERSION` is `0.3.8-dev`). No
  "Unreleased".
- Conventional Commits with scope; the body says why.

Check:
- Help text changed? Snapshots under `tests/snapshots/` (regenerate on
  purpose with `UPDATE_SNAPSHOTS=1 make test`, then read the diff).
- Flags changed? `docs/specs/INPUT.md`, `README.md.template` examples,
  the man page `docs/brew-hop-search.1.md`.
- Output changed? `docs/specs/OUTPUT.md`, `ENVELOPE.md` (fields are added,
  never removed), `SCHEMA.md`.
- New env var or setting? Defaults table, `--help=env` text, man
  ENVIRONMENT block (on the 0.4 lane: the settings table).
- New module-level state? Note it in `docs/TESTING.md` § What resets.

## Per PR

Definitely:
- CI green on every matrix entry (3.9, 3.15); `make test-all` before a
  PR that touches output. A snapshot that passes on 3.12 and fails on
  3.13 is a library-default change, not a flake: key the snapshot by the
  measured version threshold in the one test (as `test_help` does), do
  not shim the behaviour and do not skip the version.
- PR targets `dev`. Agents never push `dev` itself.
- `CHANGELOG.md` merges under the one `## [next]` heading; after merging
  `dev` in, read the top section once as a whole.
- Branch named `<type>/[<group>/]<slug>`; PR title is the squash
  message.
- Beads: `br sync --flush-only` and the jsonl committed (on dev today; on
  `chore/beads` once the lean root lands).

Check:
- Did the PR move or rename files? `grep -rn` the old paths in
  `AGENTS.md`, `docs/`, `release/`, workflows.
- Does it touch `.github/workflows/`? Permissions stay read-only at the
  workflow level; jobs grant their own.
- Does it change the test surface? `docs/TESTING.md` isolation rules.
- Is a draft spec now implemented? Move it from `drafts/` to
  `features/` or mark its Status.

## Per release (the owner's sequence, with the outside world)

Definitely, in order:
1. `dev` green on CI, changelog section read and dated
   (`## [0.3.8] — YYYY-MM-DD`).
2. `make release --skip-publish`: promotes `VERSION`, runs the suite,
   regenerates README under a clean env, tags locally, builds `dist/`.
3. Review: `git log v<prev>..dev`, the wheel's `_build_info.py`
   (`unzip -p dist/*.whl 'brew_hop_search/_build_info.py'`), the
   README diff.
4. `git push origin dev`, then `git push origin vX.Y.Z` (the
   declaration), then `git fetch . dev:main && git push origin main`.
5. PyPI: `make publish` until trusted publishing is configured; then the
   workflow does it. Confirm `uvx brew-hop-search==X.Y.Z -V` from a fresh
   target prints `X.Y.Z` with no suffix.
6. The tap (`~/dev/homebrew-tap`): bump `url` and `sha256` from the PyPI
   JSON, the `-V` test string, `brew update-python-resources`, add the
   `brew-hs` symlink when it ships; `brew style`; commit; push;
   `brew update && brew audit --new mcint/tap/brew-hop-search && brew
   reinstall mcint/tap/brew-hop-search && brew test …`.
7. Post-release bump on `dev` to the next `-dev` version and a fresh
   `## [X.Y.Z+1]` heading in the changelog.

Check:
- GitHub release notes generated by the workflow: read them once.
- `docs/meta/HISTORY.md` per-version table gains a row.
- `-VV` from the fresh install says `up to date`, install `brew` or
  `pypi`, no recent-commits block.
- Anything that names the version elsewhere: README install examples,
  the tap README table, `SECURITY.md` supported versions if present.
